# Where a KERI verification spends its time, November 2026

Fujie and Suzuki measured SD-JWT VC, W3C VCDM 2.0 with eddsa-rdfc-2022, and mdoc, and found the spread between the fastest and slowest format to be about 0.27 ms per exchange, while resolving the issuer's key, checking status and checking holder binding, which they did not measure, were said to cost one to three orders of magnitude more (arXiv:2611.03493; read here through the plan's summary of it, `~/.local/state/zamu/plans/vc-harden/briefs/papers-summary.md`, not the paper itself). This report measures those other costs for a KERI verifier, stage by stage, and times the three derivative formats on the same host, so the two can be set side by side. Why it is measured this way is `this.i` 3jeks5st and its child; what each derivative row does is [`scripts/derivatives/README.md`](../scripts/derivatives/README.md).

## The answer

On this host a warm heti verification of a presented ACDC took 311 ms at p50 and 521 ms at p99. Signature verification was 0.24 ms of that, about 0.1%. Key state was 76%: 160 ms for the issuer's, gathered twice per verification, and 77 ms for the holder's. TEL status was 13%, 15 ms reading the Observer and 26 ms judging the chain. The derivative formats verified in 1.2 to 3.7 ms at p50 on the same host. So the spread between those formats, about 2.5 ms here, is under 1% of the KERI verification's own cost. Nearly all of that cost is in what the papers left out, and on this stack almost none of it is cryptography.

In the papers' terms, per exchange:

| | p50 ms | p99 ms | share of the KERI verification |
|---|---|---|---|
| KERI: issuer key state (two witness gathers and replays) | 159.7 | 361.2 | 52% |
| KERI: holder binding (holder key state and the grant's signatures) | 77.5 | 127.5 | 25% |
| KERI: status (Observer read, TEL judged against the issuer's KEL) | 41.2 | 77.3 | 13% |
| KERI: everything else (parsing, schema, SAIDs, disclosures) | 27.9 | 75.9 | 9% |
| KERI: IPEX admit receipt (signing, not checking) | 1.3 | 3.8 | 0.5% |
| KERI: whole verification | 311.2 | 521.1 | |
| SD-JWT VC, 5 of 20 disclosed, with key binding (arf-interop `verify_eaa`) | 1.59 | 2.71 | |
| SD-JWT VC, 5 of 20 disclosed, no key binding | 1.20 | 2.05 | |
| W3C VC, eddsa-rdfc-2022, 20 attributes (two RDFC canonicalizations) | 3.75 | 6.89 | |
| W3C VC, eddsa-rdfc-2022, 5 attributes, re-signed | 3.64 | 6.39 | |
| mdoc, 5 of 20, mdoc-interop warm in one JVM | 2.37 | 8.67 | |
| mdoc, 5 of 20, mdoc-interop CLI, a process per verification | 655.9 | 887.3 | |

The KERI percentiles are each stage's own distribution, so the rows do not add to the total's; the shares are of summed time. The derivative rows include the network checks they need only because none was needed: anchors and keys were held in memory and no status list was fetched. The KERI rows include every network call a heti verifier makes, which is the point of measuring them.

## The KERI stages

`heti.timed_verifier` wraps heti 3a8b1ccb's own stage functions inside the verifier process and charges each call to the verification running in that task (`src/keri_bench/stacks/stages.py`; `docs/adapters.md`). The scenario is the lifecycle to verified, one home, at 0.5 credentials a second for 240 s (`scenarios/verify/verify-stages-1home.toml`), so no two verifications ran together. The scenario declares three repetitions, as every scenario must, and `scripts/verify.sh` runs one of them, at the scenario's rate, as `scripts/baseline.sh` runs a soak. 120 credentials verified. 259 attempts were made: 139 were refused with `e.state.pending.registry.r`, the verifier asking before the Observer held the registry, and asked again 250 ms later, and those are left out. The first attempt, which met the holder, was one of them, so every accepted attempt was warm: 120 warm verifications, all summarised in [`results/verify-2026-11/verify-stages-1home/rate-0.5/rep-1/stages.md`](../results/verify-2026-11/verify-stages-1home/rate-0.5/rep-1/stages.md):

| stage | calls | p50 ms | p99 ms | mean ms | share |
|---|---|---|---|---|---|
| key_state.issuer | 2 | 159.65 | 361.23 | 166.50 | 52.2% |
| key_state.holder | 1 | 77.20 | 127.27 | 79.03 | 24.8% |
| tel.vet | 4 | 26.33 | 57.18 | 25.29 | 7.9% |
| tel.fetch | 1 | 15.01 | 26.35 | 16.49 | 5.2% |
| receipt | 1 | 1.33 | 3.80 | 1.51 | 0.5% |
| signatures | 1 | 0.24 | 1.01 | 0.29 | 0.1% |

The time inside heti's two calls was 196 ms in `admit` and 106 ms in `verify_current_acdc` at p50. One-off costs, for a verifier meeting a party for the first time: opening the verifier's lockbox, which resolves the issuer's OOBI and replays its KEL, took 127 ms, and meeting the holder at its first presentation took 171 ms.

Four things in these numbers are worth reading carefully.

The issuer's key state is gathered twice per verification. The bench's verifier calls heti's `admit`, which verifies the presenter's own TEL and binds the presenter, and then `verify_current_acdc`, which verifies again on the Observer's TEL; each asks the issuer's witnesses. A verifier that trusted only the Observer's TEL could skip the first full verification, and the issuer key state would then cost one gather. That is a choice in the bench's verifier (`src/keri_bench/stacks/verifier.py`), mirroring the summit harness, not in heti.

Key state is a witness gather on every verification because heti's default key-state plan is to ask the witnesses, then fall back to what is held (heti `src/heti/anchored/produce/keystate.py`). keri-bench's stack has no watcher. A plan that reads a watcher, or one that judges a recently gathered KEL as held, would change the largest stage, and is the obvious next measurement (tick 4ul3).

Each gather here takes about 80 ms, and every witness is on loopback. So this is not network latency; it is the time heti and keripy take to query, receive and replay through the harness's proxy. The wrappers cannot divide that time between fetching and replaying, and nothing here says where inside the gather it goes; a profile of `Lockbox._resolve_other` would (tick 57wk). A deployment with real round trips to witnesses would add those on top.

The cryptography is a rounding error. The one Ed25519 check outside KEL replay, the grant's signatures against the holder's key state, took 0.24 ms, against 0.09 ms for one bare `Verfer.verify` in keri-bench's October microbenchmark on this host ([`results/baseline-2026-10/microbench.json`](../results/baseline-2026-10/microbench.json)); the rest is reading the key state and the threshold. The issuer's signature on an ACDC is its anchor in the issuer's KEL, which `tel.vet` checks as a seal lookup, not as a signature.

## The derivative formats

[`results/verify-2026-11/derivatives.json`](../results/verify-2026-11/derivatives.json), 2,000 timed verifications per row after 200 untimed, except the CLI row, which is 30 processes after three untimed, so its p99 is its maximum; in arf-interop's own environment at arf-interop 62b961c (its `vc-harden` branch), pyld 3.3.0, joserfc 1.7.4, cryptography 50.0.1, and mdoc-interop ad5f03f on OpenJDK 25.0.4.1.

The ordering reproduces the papers': Data Integrity is the slowest, at 2.3 to 3.1 times SD-JWT VC here (with and without key binding) against the papers' 1.6 to 2.0 times, and one RDFC canonicalization alone costs 1.5 to 1.6 ms, so the two per verification are most of the row. The absolute numbers are well above the papers' Node figures, as the plan's summary gives them for a cloud VM: SD-JWT VC 1.20 ms against 0.298, about four times; Data Integrity 3.75 against 0.534, about seven; mdoc 2.37 against 0.265, about nine. Those were for a whole exchange, issuing and presenting as well as verifying, where these rows verify only. These are Python libraries, and arf-interop's `verify_eaa` walks an X.509 chain and checks the key-binding JWT, so the rows measure a fuller verifier on a slower runtime, not the same thing on the same one. mdoc in one warm JVM took 2.37 ms, including reading two files and rendering mdoc-interop's evidence record, which its CLI does on every call; mdoc-interop checked everything but device authentication, which was not asked for. Run as it is deployed, a process per verification, it took 656 ms, nearly all of it the JVM starting, so at that size an mdoc verification through the CLI costs twice a whole KERI verification, for reasons that are not the format's.

## The host and the run

kelun: Intel Core (Haswell, no TSX), 8 cores, 23 GB, Linux 7.0.0-38, Python 3.14.6, keri-bench 225be09, imbu 7ff15e6a, heti 3a8b1ccb. The run was not at nice 19, since per-call latencies are what a deprioritised process inflates. Two other sessions on the host paused their benchmarks and test suites for it, at this run's request. What still ran is in [`results/verify-2026-11/host.log`](../results/verify-2026-11/host.log): an editor agent at about a third of a core and two nice-19 JVMs at a quarter each, then two jshell processes by the end. The one-minute load average, including the stack's own processes, stayed between 3.2 and 4.3 over the window ([`loadavg.log`](../results/verify-2026-11/loadavg.log)). The harness's calibration passed on this attempt; the first attempt's calibration was refused by 0.1 ms while another session's parallel tests ran, and it is not reported.

## Limits

- One holder, one issuer home, a credential with no edges, and an issuer KEL that grows by about one event a credential to 120. Edged credentials walk their far nodes, each with its own issuer's key state, and would cost more.
- The stages are wall-clock time on one event loop. The run kept verifications from overlapping, and the summary drops any that did, but other work on the verifier's loop during an await, such as receipting its own facet's events, is charged to whichever stage was open. There was little such work here, and none of it is excluded.
- Only the issuer's key state and the holder's are labelled apart, by the grant's sender. A self-issued credential would charge both to the holder's.
- The wrapped names are heti 3a8b1ccb's private functions; on a repin the timed verifier refuses with `e.feature.unsupported.stages.heti.f` until the wrappers are updated.
- The KERI percentiles come from keri-bench's histogram and the derivative ones from nearest rank; at these sample sizes the difference is below the precision quoted.
- The mdoc rows have no device authentication and the W3C rows resolve no DID document and check no status, so each derivative row is the format's own checks with every network step taken out, which is the papers' scope and not a deployment's.

## Reproducing it

```
uv sync --extra stacks
scripts/verify.sh runs/verify results/verify-2026-11 <arf-interop vc-harden checkout> \
    <mdoc-interop>/build/install/mdoc-verify
```

`scripts/verify.sh` says how to run it under a user unit, and `scripts/derivatives/README.md` how to set up the two checkouts. `SHA256SUMS` in the results directory covers every file.
